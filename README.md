# Laravel Book Catalog Application

Учебный проект, демонстрирующий погружение в архитектуру фреймворка **Laravel**, оптимизацию высоконагруженных баз данных и работу с асинхронной архитектурой.

## 🛠 Технологический стек
* **Backend:** PHP 8.5, Laravel 13
* **Databases:** MySQL 8.4
* **Caching & Queues:** Redis, MySQL Queue Driver
* **Testing:** PHPUnit
* **VCS:** Git
---

## 🚀 Ключевой функционал и архитектурные решения

### 1. Оптимизация БД и Eloquent ORM
* **Оптимизация:** Для работы с таблицами высокой плотности отключены встроенные поля времени (`$timestamps = false`), что снижает нагрузку на память.
* **Кастомные связи:** Реализовано переопределение стандартных конвенций Laravel с использованием кастомных внешних ключей (`bookId` и `authorId`).
* **Связи Many-to-Many:** Настроена работа с Pivot-таблицами через методы `attach()` и `syncWithoutDetaching()` без ручного написания SQL-запросов. Используется безопасный массовый ввод через `$fillable`.
* **Инкапсуляция логики (Scopes):** Реализованы локальные области видимости (Scopes) для инкапсуляции сложных SQL-запросов (включая `EXISTS` через `whereHas`).

### 2. Фоновые процессы и Асинхронность (Queues & Redis)
* Настроена и протестирована работа очередей на драйверах `database` и `Redis` (с учетом специфики изоляции IP в Open Server Panel 6).
* Реализована асинхронная задача `ProcessBookView` для обновления счетчика просмотров без блокировки основного потока пользователя.
* Изучена архитектура очередей изнутри: защита от потери задач (ACK / `:reserved`) и отложенный запуск через `delay()`.
* Обработана отказоустойчивость CLI-команд: защита от дедлоков в БД и использование встроенного механизма повторных попыток задач (`$tries`).

### 3. Архитектура приложения и Паттерны
* **Repository & Service:** Бизнес-логика вынесена из контроллеров. Реализован паттерн *Repository* для низкоуровневых запросов через фасад `DB`, и *Service* — для ветвления логики поиска.
* **Разделение обязанностей (Traits vs Classes):** Чистые функции (транслитерация) вынесены в изолированные утилиты, а логика моделей — в гибкие трейты с инициализацией через метод `booted()`.
* **Dependency Injection:** Активно применяется сервис-контейнер Laravel и автоматическое разрешение зависимостей (Auto-wiring) через Type Hinting в контроллерах.

### 4. Маршрутизация, SEO и Полнотекстовый поиск
* **SEO-маршруты:** Реализован универсальный SEO-маршрут для книг через регулярные выражения. Написана логика дешифровки путей, выполняющая автоматический `301-редирект` на каноничный URL при несоответствиях.
* **Защита от N+1:** В каталоге книг внедрена жадная загрузка (*Eager Loading*) через `with('authors')` в связке со встроенной пагинацией.
* **Full-Text Поиск:** Спроектирован сложный составной полнотекстовый индекс в миграциях MySQL. Поиск авторов переведен на режим `BOOLEAN MODE` с помощью `whereRaw()`.

### 5. Безопасность, Blade и Тестирование
* **Безопасность:** Внедрена и настроена защита форм от межсайтовой подделки запросов (CSRF) с помощью посредника `VerifyCsrfToken`.
* **Blade:** Реализован полиморфный вывод данных (Книги/Авторы) в одном цикле с использованием `instanceof`. Кастомизированы системные шаблоны пагинации.
* **Автоматическое тестирование:** Написаны функциональные (Feature) тесты на PHPUnit для проверки поисковой выдачи. Решена проблема конфликта SQLite (in-memory) с полнотекстовыми индексами MySQL с помощью тестовой БД.

### 6. Изучение Git
* **Команда статуса:** `git status` Вызывается для отображения текущей ветки и новых/изменённых файлов. Опции:
    * `-s` - сокращённый вывод файлов, если их много
    * `-b` - вывод только ветки
* **Команда добавления в индекс:** `git add .` Эта команда добавит в индекс все изменённые файлы в ветку. Точка означает всё в этой директории. Можно вместо точки написать имя файла.
* **Команда удаления из индекса:** `git restore --staged README.md` Эта команда уберёт из индекса конкретный файл.
* **Команда создания коммита:** `git commit` Эта команда закоммитит изменения. Создаст "снимок" проекта. Опция `-m "Some message"` позволяет добавить комментарий к коммиту.
* **Команда изменения коммита:** `git commit --amend --no-edit` Это позволяет добавить/исправить файлы в коммит (`--amend`) без изменения сообщения (`--no-edit`). Перед этой командой нужно проиндексировать изменения.
* **Команда удаления коммита:** `git reset --soft HEAD~1` Это позволяет удалить последний коммит (`HEAD~1`), но сохранит изменения в индексе (`--soft`). Также можно удаить коммит по его хэшу (вместо `HEAD~1`).
* **Команда пуша:** `git push origin main` Эта команда пушит все коммиты с ветки `main` в имя удаленного репозитория (`origin` по умолчанию)
* **Как пушить определённые коммиты:** Безопасный и правильный способ - через создание новой ветки:
    * `git branch` посмотреть список всех локальных веток. Та ветка, у которой стоит звездочка * и которая подсвечена зеленым — текущая.
    * `git checkout -b feature/my-new-feature` создать ветку и переключиться на неё. Если в 2 команды:
        * `git branch feature/my-new-feature`  Создали ветку или без /: `git branch feature`
        * `git checkout feature/my-new-feature` Переключились на неё
    * `git cherry-pick <хэш_нужного_коммита>` cherry-pick эта команда берет один конкретный коммит из любой другой ветки и копирует его в твою текущую ветку. Забираем в эту ветку только коммит с исправлением бага.
    * `git push origin <название-ветки>` пушим конкретную ветку.
* **Зачем нужен stash:** `git stash` (заначка) работает с незакоммиченным кодом (с файлами, которые горят красным или зеленым в `git status`). Это временный карман, куда ты можешь спрятать свои текущие недописанные изменения, чтобы сделать рабочую директорию абсолютно чистой.
Действия с использованием `stash`:
    * `git stash` Прячешь всё недописанное в «заначку».
    * Переключаешься в нужную ветку, чинишь условный баг.
    * Возвращаешься обратно в свою ветку.
    * `git stash pop` Достаешь свои недописанные файлы из заначки обратно в рабочую зону.<br/>
!) Если в заначке тоже были изменения:<br/>
Произойдёт конфликт, если в одном файле в одной строке были изменения.<br/>
В терминале появится что-то вроде сообщения: `CONFLICT (content): Merge conflict in <файл> The stash entry was kept in case you need it again.`<br/>
Через VS Code:<br/>
	* Посмотри на файлы. В `git status` конфликтующие файлы будут помечены как `both modified`.
	* Открой файл в VS Code. Ты увидишь специальную разметку Git, которая выглядит так:
		```
        <<<<<<< Updated upstream
		Новый код, который уже был в ветке (например, фикс бага)
		=======
		Старый код, который ты достал из заначки (stash)
		>>>>>>> Stashed changes
        ```
	* Выбери правильный вариант. Прямо над этими строками в VS Code появятся кликабельные кнопки-помощники:
		* `Accept Current Change` — оставить код, который был в ветке.
		* `Accept Incoming Change` — взять код из заначки.
		* `Accept Both Changes` — сохранить оба варианта друг за другом.
		* Также ты можешь просто вручную стереть разметку Git (<<<<<<<, =======, >>>>>>>) и написать финальный код руками.
	* Сохрани файл
	* После того как конфликт решен, нужно проиндексировать файл: `git add index.php`
		* Если это был конфликт при слиянии веток, ты бы сделал `git commit`. Но так как это был stash, твои файлы просто успешно вернулись на рабочий стол.
	* Очисти заначку: Так как из-за конфликта заначка осталась в памяти, удали её вручную, когда убедишься, что код восстановлен правильно: `git stash drop`
* **Работа со слиянием веток:**
    * `git merge <сливаемая-ветка>` Вызывать эту команду надо **находясь** на ветке **в** которую надо слить.<br/>
    Произойдёт слияние веток. Если будет конфликт, то увидим:
	```
    Auto-merging README.md
	CONFLICT (content): Merge conflict in README.md
	Automatic merge failed; fix conflicts and then commit the result.
    ```
    Если ввести `git status`, то файл README.md находится в статусе `both modified`.
    * Разметка конфликта:<br/>
    Если открыть README.md через обычный блокнот или посмотреть в консоли, то Git прямо в текст файла вставил специальные маркеры разделители:
	    ```
        <<<<<<< HEAD
	    Текст, который ты написал, находясь в ветке main
	    =======
	    Текст, который прилетел из ветки branch-learnings
	    >>>>>>> branch-learnings
        ```
    Описание маркеров:
        * `<<<<<<< HEAD` — начало изменений из твоей текущей ветки (main).
        * `=======` — граница между твоим и чужим кодом.
        * `>>>>>>> <название-ветки>` — конец изменений, которые пришли из вливаемой ветки.
    * Разрешение конфликта:<br/>
    В VS Code появятся кнопки для мерджинга. (Они плохо видны - фото есть):
	    * `Accept Current Change` — оставить код, который был в ветке.
	    * `Accept Incoming Change` — взять код из заначки.
	    * `Accept Both Changes` — сохранить оба варианта друг за другом.
	    * `Compare changes` -
    Если не через VS CODE, то просто вручную стереть строчки с `<<<<<<< HEAD`, `=======` и `>>>>>>> branch-learnings`. Сформировать финальный текст. Оставить внутри файла вариант текста, который должен пойти в финальную версию проекта.
    Нажав `Accept Incoming Change`, при вызове статуса появится ещё строки:
	```
    On branch main
	Your branch is ahead of 'origin/main' by 2 commits.
	  (use "git push" to publish your local commits)

	You have unmerged paths.
	  (fix conflicts and run "git commit")
	  (use "git merge --abort" to abort the merge)

	Unmerged paths:
	  (use "git add <file>..." to mark resolution)
        	both modified:   README.md
    ```
    * Завершение мерджа:<br/>
        * `git add README.md` - После сохранения файла надо добавить исправленный файл в индекс.
        * `git commit -m "Merge branch-learnings into main and fix conflicts"` - Сделать финальный коммит слияния.
        > Если ты введешь просто `git commit` без флага `-m`, Git сам откроет текстовый редактор и предложит стандартное сообщение вроде `"Merge branch 'branch-learnings'"`.
        * `git push origin main` Пушим наш коммит слияния
* **Работа с удалением веток:** Локальные и удаленные временные ветки нужно удалять. Если этого не делать, через пару месяцев репозиторий превратится в «кладбище веток», в котором будет невозможно ориентироваться. Когда ветка уже успешно слита с основной веткой на GitHub, ее можно смело удалять. Удаление происходит в 2 этапа:
    * Удалить ветку локально:
        * Сначала переключиться на другую ветку, тк Git не позволит удалить ветку, на которой ты стоишь.
		* `git branch -d <название-ветки>` Если Git ругнется, что ветка не полностью слита, но ты уверен, что она больше не нужна, замени строчную -d на заглавную -D (принудительное удаление).
    * Удалить ветку на сервере.
        * `git push origin --delete <название-ветки>`
* **Откат мерджа:** `git merge --abort` Эта команда позволяет полностью отменить мердж.
